# Aurora Location

[中文](README.md)

Aurora Location is a personal iPhone development and testing tool for simulated location. Its SwiftUI and MapKit interface selects a coordinate, then uses Apple DVT `LocationSimulation` to request a simulated or restored real location. It does not modify third-party apps, provide detection evasion, or target App Store distribution.

The project implements an on-device iOS 27 `Remote Pairing` flow and establishes its developer connection through an existing single-VPN Shadowrocket setup. User physical-device feedback confirms successful simulated location with Aurora Location + Shadowrocket single VPN, and both the system pairing list and saved App pairing record have been confirmed. That does not establish every scenario: the complete set/change-point/clear matrix, Apple Maps rechecks, foreground/background retention, and new cellular connection remain physical-device acceptance work in the [test plan](docs/TEST_PLAN.md).

## Features

- On-device iOS 27 Remote Pairing wizard, six-digit PIN, cancellation, and protected local pairing record.
- Map tap and long-press selection, search, reverse geocoding, and manual coordinates.
- Local favorites and up to 20 deduplicated recent locations.
- Strict `auroralocation` URL Scheme validation, Chinese error messages, and redacted diagnostics.
- Export of a device-generated local WireGuard peer and Shadowrocket routing module.

`Last operation` means only that the App-side command completed. It does not report the current system simulation state. Every launch begins in an unknown state; verify with Apple Maps or the app under test.

## Requirements

- macOS and Xcode. The app deployment target is iOS 18.0. Xcode 26.6 with iPhoneOS SDK 26.5 is a recorded build reference, not a minimum-version promise.
- An iPhone with Developer Mode enabled. The current first on-device Remote Pairing implementation requires iOS 27.
- A usable Apple Developer signing identity and provisioning. Xcode must have prepared the device and made DDI services available.
- Shadowrocket that can import a local WireGuard peer and module within the existing single-VPN configuration. Version 2.2.92 (3445) is a recorded compatibility reference, not a minimum-version promise. A second VPN app is unnecessary.
- An arm64 physical device. Native static libraries have no Simulator slice.

## Source and build

```sh
git clone https://github.com/AuroraNest/Aurora-Location.git
cd Aurora-Location
sh scripts/check.sh
```

`scripts/check.sh` runs URL/coordinate and local-storage model checks, an FFI-session stub check, and plist lint. It is not a device-protocol or simulated-location acceptance test.

Open `AuroraLocation.xcodeproj` in Xcode and select the `AuroraLocation` scheme. Under `Signing & Capabilities`, select your own Developer Team, use `Automatically manage signing`, and change to your own unique Bundle ID. The repository includes no Team ID, signing certificate, or provisioning profile. To keep a local Team selection in configuration, create an untracked `Signing.xcconfig`; the existing configuration includes it optionally.

For an unsigned device build:

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer xcodebuild \
  -project AuroraLocation.xcodeproj -scheme AuroraLocation \
  -configuration Debug -destination 'generic/platform=iOS' \
  -derivedDataPath build/DerivedData CODE_SIGNING_ALLOWED=NO build
```

Then connect and unlock the device, enable Developer Mode, and Run from Xcode with that device selected. A signed build, install, or launch proves only the installation path. It does not prove that `set` or `clear` changed system location.

## Configure the local Shadowrocket WireGuard peer

The configuration uses keys generated by the app for the current device. Do not write it manually, reuse it, or share it with another device.

1. In Aurora Location, open Settings and tap `复制小火箭连接配置` (Copy Shadowrocket connection configuration).
2. In Shadowrocket, import the WireGuard node from the clipboard. Set its actual name or remark to **`AuroraLocal`**. The module refers to this name, including its case.
3. Return to Aurora Location Settings, tap `复制本机分流模块` (Copy local routing module), then import and enable it from the Shadowrocket clipboard:

```ini
#!name=Aurora Local
#!desc=Local developer connection only
[Rule]
IP-CIDR,10.7.0.1/32,AuroraLocal,no-resolve
```

4. Keep the daily proxy node as the default policy. The module sends only `10.7.0.1/32` to `AuroraLocal` and should not take ordinary traffic. Reconnect the Shadowrocket system VPN after enabling the module. Do not overwrite an existing subscription or change `skip-proxy`, `tun-excluded-routes`, or `compatibility-mode` by default.
5. Return to the app and tap `重新检测` (Recheck). A TCP-ready result only means that the port is reachable; it is not new proof of Remote Pairing or DVT success.

The exported peer uses local endpoint `127.0.0.1:51820`, client address `10.7.0.10/24`, and `AllowedIPs = 10.7.0.1/32`. The native responder accepts only authenticated IPv4 TCP traffic to that reserved address on dynamic ports. Dynamic ports are required, so do not restrict routing to initial port `49152`.

The app keeps the exported connection configuration only in the local clipboard for two minutes. It includes this device's WireGuard private key. It excludes the Apple pairing record, but must still never be uploaded to subscriptions, Git, logs, or chat.

## First Remote Pairing

1. Confirm Shadowrocket is connected, Developer Mode is enabled, and Xcode has prepared the device.
2. Connect the iPhone to Wi-Fi. Initial Bonjour pairing requires Wi-Fi.
3. In Aurora Location Settings, tap `开始配对` (Start pairing), grant Local Network and notification permissions, and keep the app foregrounded.
4. Open system `Settings > Privacy & Security > Developer Mode > Pair with Host`, then select Aurora Location.
5. Enter the device passcode first, then the six-digit PIN shown in the app or local notification.
6. Return to the app, confirm that a pairing record is saved, then tap `重新检测` (Recheck).

Pairing waits for about three minutes. iOS grants only limited execution time when the app backgrounds. After cancellation, timeout, or an incorrect PIN, return to the app and retry. Never copy the PIN into diagnostics or external services. After pairing, the app does not preemptively reject `set`/`clear` just because it cannot read a Wi-Fi interface address; success still depends on the live handshake.

## Set and clear location

Choose a map point by tap or long press, search, or enter coordinates. Tap `开启模拟定位` (Start simulated location), then check the result in Apple Maps. Tap the fixed bottom `恢复真实定位` (Restore real location) button and check Apple Maps again.

The first `set` starts the local responder and creates a DVT session. While that session is retained, later `set` and `clear` calls reuse it rather than reconnecting every time. `clear` closes the DVT session and responder. When no in-memory session exists, the `clear` implementation creates a new connection to send the restore request. A failed operation releases both resources; the next operation reconnects.

This describes implementation behavior, not device acceptance. The reconnect path for `clear` after an app restart exists but still needs physical-device verification. If a network failure prevents `clear` from completing, location state is unknown.

## Shortcuts and URL Scheme

In Apple Shortcuts, create a `URL` action and pass it to `Open URLs`:

```text
auroralocation://set?lat=40.7580&lon=-73.9855
auroralocation://clear
```

`set` accepts only finite `lat` and `lon`: latitude from -90 to 90 and longitude from -180 to 180. Duplicate, missing, or extra parameters, fragments, userinfo, ports, invalid paths/schemes, `NaN`, and `Infinity` are rejected. URLs and UI controls share pairing and network gates. There are no App Intents, background automation, or scheduled retries.

## Troubleshooting

| Symptom | Check first |
| --- | --- |
| Aurora Location is absent from Pair with Host | iOS version, Developer Mode, Wi-Fi, Local Network permission, and that the app remains foregrounded. |
| PIN is absent or pairing times out | Notification permission, the system Pair with Host flow, and that passcode then PIN were entered in order. Cancel and start pairing again. |
| Recheck reports an unreachable port | Confirm Shadowrocket is connected as the system VPN, the local WireGuard peer is imported, and the module is enabled. |
| Port is reachable but handshake fails | Confirm the node is actually named `AuroraLocal`, the module refers to that name, then inspect Shadowrocket routing/connection records for the local address. TCP-ready does not prove a service response. |
| WireGuard has counters but DVT fails | Counters only show local data-plane receipt, authentication, or reflection. Check Developer Mode and Xcode device preparation/DDI. |
| Map does not change after set/clear | Do not rely on Last operation. Verify with Apple Maps, check Shadowrocket and the developer connection, and treat a failure as unknown state. |
| Location restores after backgrounding or lock | This is a known limitation. The exported peer has WireGuard `PersistentKeepalive = 25`, but the app does not use iOS background audio, automatic retry, or a background keep-alive mechanism to retain simulation. |

## Privacy and security

- Pairing records and WireGuard keys live in Application Support with Complete Data Protection, owner-only directory permissions, and backup exclusion.
- PINs are not logged. Redacted diagnostics contain only version, pairing-present state, network/service state, responder counters, and fixed error codes.
- Favorites and history are local only. There are no accounts, analytics, self-hosted servers, or cloud sync.
- MapKit search, maps, and reverse geocoding use Apple services, so those features are not fully offline.
- Connection configuration and pairing records are sensitive. Deleting the app or its data can remove local credentials, requiring new pairing and peer export.

## Limits and acceptance boundary

- Simulated location is not promised to persist indefinitely in the background. iOS may restore real location after suspending or terminating the app.
- New cellular-only sessions, retention across Wi-Fi-to-cellular transition, new sessions on Wi-Fi without internet, clear after restart, and behavior in all target apps remain unverified.
- User physical-device feedback confirms single-VPN simulated location, but the full set/change-point/clear, Apple Maps, restart, foreground/background, and cellular acceptance matrix remains incomplete.
- The app does not download or mount DDI. If developer services fail, prepare the device again in Xcode.
- There is no joystick, GPX, route playback, account, cloud sync, detection evasion, embedded VPN, or Simulator DVT.

Use unchecked entries in [docs/TEST_PLAN.md](docs/TEST_PLAN.md) as the actual acceptance checklist. [docs/SHADOWROCKET.md](docs/SHADOWROCKET.md) records the single-VPN evidence and limits.

## Rebuild third-party native libraries

The repository includes matching arm64 iOS static libraries and C headers. Do not replace one artifact: `idevice.h` and `libidevice_ffi.a` must come from the same build.

Rebuilding `Vendor/idevice` requires Git, Xcode/iPhoneOS SDK, Rust 1.93.1 with the `aarch64-apple-ios` target, and upstream repository plus Cargo registry access:

```sh
scripts/build-idevice.sh
```

The script pins the upstream commit, lock file, and patch; restores source in an isolated build checkout; builds with `--locked`; and checks exported symbols. Set `IDEVICE_BUILD_DIR` only to a disposable checkout. The script resets that directory.

Rebuilding the local WireGuard responder also requires Rust 1.93.1, the iOS target, and its pinned `Cargo.lock`:

```sh
cargo test --locked --manifest-path Vendor/emproxy/Cargo.toml
scripts/build-emproxy.sh
```

These commands validate native components. They do not replace physical-device Remote Pairing or location acceptance. See [Vendor/idevice/SOURCE.md](Vendor/idevice/SOURCE.md), [Vendor/emproxy/README.md](Vendor/emproxy/README.md), and [third-party notices](THIRD_PARTY_NOTICES.md).
